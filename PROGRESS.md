## Notable fixes made during execution (beyond the original plan)

Caught in the pre-flight conflict scan before any code was written (see plan's revision history in `git log -- docs/superpowers/plans/`):
- HR/LR size mismatch between the backbone's fixed 64x64→1024x1024 (16x) assumption and the original 256x256 dataset defaults — standardized on 1024x1024 throughout.
- Signal S2 was wired up with a no-op stand-in that made it mathematically zero everywhere — replaced with `estimate_prior_reliance_map` (Task 5), a real LR/seed-perturbation estimator.
- Per-epoch recomputation of signal stacks would have made one epoch of fusion-head training take days — added `precompute_signal_stacks` caching.
- The disentanglement metric (spec Section 5, item 5) was imported but never called in the evaluation script — wired up via a new `signal_stack` field on `run_chasr`'s return dict.

Caught during Task 2's review:
- `degrade_standard` recorded a `sigma` in its ground-truth params that didn't match the sigma actually used to build the blur kernel (double-sampled from the RNG stream). Fixed by having `sample_standard_kernel` return `(kernel, sigma)` instead of just the kernel.

Caught during Task 4's review:
- `ddnm_project` used `.view()` on `x_hat`/`y` instead of `.reshape()`, which would raise `RuntimeError` on non-contiguous tensors — plausible for real diffusion sampler outputs (post-`permute`/batched-index results) once wired into Task 5's backbone wrapper. Fixed by switching to `.reshape()`, matching the pattern already used for the output; added a regression test with a non-contiguous input tensor plus tests for the general (non-identity) null-space invariant and the `scale=1` degenerate case.

Environment note (2026-08-26, second machine): `opencv-python`, `diffusers`, `lpips`, and `easyocr` from `requirements.txt` were not yet installed in this machine's `py313` conda env — installed via `pip install -r requirements.txt` (split into two calls after a mid-download connection reset). No code changes; flagging in case other machines hit the same gap.

Caught during Task 5's review (code-reviewer agent, before any real-model run) and confirmed live on GPU:
- `ddnm_project(hop1, lr_patch, ...)` (and the tile/final-stitch calls) did plain tensor arithmetic between a CUDA fp16 pipeline output and a CPU fp32 `lr_patch`/`stitched` buffer — would raise a device-mismatch `RuntimeError`. Fixed by casting the reference tensor to the pipeline output's actual device/dtype at each stage instead of assuming CPU fp32.
- `estimate_prior_reliance_map`'s S2 formula divided `g_evidence` by `eps` (a true finite-difference derivative) but left `g_prior` (a discrete reseed, no natural step size) un-normalized — biases every real, non-degenerate pipeline toward S2≈0 regardless of actual behavior, since the two terms aren't on comparable scales. Fixed by comparing raw (non-eps-normalized) output-magnitude changes for both terms instead; added a `_MixedSensitivityPipeline` test exercising a non-degenerate case (both stub tests before this only covered the two 0%/100%-sensitivity extremes, which don't distinguish the buggy formula from the fixed one).
- `scripts/smoke_test_backbone.py` (plan's Step 5 deliverable) hadn't been written yet — added, and extended beyond the plan's shape-only assertion to also save a visual comparison (LR input, bicubic baseline, 2 stochastic SR samples, and a null-space-variance preview) to `outputs/smoke_test_backbone/` (git-ignored).

Caught only by actually running the real model on GPU (none of the above were catchable from stub-based unit tests or static review alone):
- `StableDiffusionUpscalePipeline.__call__` requires `prompt` or `prompt_embeds` — the plan's original `_upscale_4x` passed neither, so the very first real call raised `ValueError`. Fixed by passing `prompt=""` (text-free upscaling, matching the backbone's blind/domain-agnostic framing). The stub pipelines in the test file didn't declare a `prompt` parameter at all, so this drift was invisible to pytest — added an `assert prompt is not None` guard in the stub as a regression trip-wire.
- The pipeline also requires a **batched** `(1, C, H, W)` image tensor — passing the documented-shape `(C, H, W)` tensor made `check_inputs` read the channel dimension as a batch of 3 single-channel images and raise a batch-size-vs-prompt mismatch. Fixed with `patch.unsqueeze(0)` in `_upscale_4x`. (The installed `diffusers==0.31.0`'s `VaeImageProcessor.preprocess` — inspected during Task 5's code review — appeared to auto-unsqueeze a 3D input, but the actual installed/working version, 0.40.0 per the next bullet, does not; static source-reading of a library is not a substitute for running it.)

Also added `variant="fp16"` to `from_pretrained`, which wasn't in the plan's original code — without it, diffusers downloads the full fp32 checkpoint (~5GB) and casts locally instead of fetching the ~4x-smaller pre-quantized fp16 files (~1.7GB total), which matters a lot under the network conditions below.
- `huggingface_hub`'s own downloader (both its Xet fast-transfer backend and its plain-HTTP fallback via `HF_HUB_DISABLE_XET=1`) stalled indefinitely on this machine's network — near-zero throughput for many minutes — while plain `curl` to the identical resolve URLs ran at several MB/s (with the underlying network itself periodically dropping long-lived connections, requiring resumable/retrying downloads). Worked around by `curl`-downloading the three fp16 weight files by hand into `checkpoints/stable-diffusion-x4-upscaler/` (git-ignored) and adding a `model_id` constructor parameter to `DiffusionSRBackbone` (defaults to the hub repo id, unchanged for normal use) so a local snapshot directory can be substituted — exposed via `CHASR_MODEL_ID` in the smoke script. Root cause not diagnosed further (likely a proxy/CDN-path difference between `huggingface_hub`'s client and raw HTTP); worth re-testing on a different network before assuming this is permanent.
- **Must pass an absolute path** to `model_id` when using the local-checkpoint override — a relative path (`checkpoints/stable-diffusion-x4-upscaler`) contains exactly one `/`, which `from_pretrained` can misparse as a `org/repo`-shaped hub id rather than a local directory (depending on `cwd` at call time), silently falling back to hub resolution and hanging with zero GPU activity instead of raising a clear error.

**Known cosmetic limitation, not yet fixed:** the 2x2 tile-stitching in `sample_k_16x` has no overlap/blending, so real outputs show a faint grid-seam artifact at the tile boundaries (visible in the Task 5 demo images). Not blocking — DDNM projection still enforces exact data consistency across the seams — but worth revisiting (e.g. overlapping tiles + linear blend) if later signal quality is affected.

Task 6 (`compute_null_space_variance`) matched the plan verbatim and passed code review with no HIGH/CRITICAL findings — only a MEDIUM (no test pinned the unbiased-variance estimator choice against a silent scale-changing regression; added `test_variance_matches_unbiased_formula` with hand-computed expected values) and a LOW (moved a nested `import pytest` to module scope). Note for Task 12: production usage calls this with `k=2` (per the plan's `build_signal_stack`), which is a very small sample for a variance estimate — noted as a design consideration for that task, not a defect here.

Task 7 (`compute_prior_reliance`) matched the plan verbatim and passed code review with no HIGH/CRITICAL findings. The review specifically checked whether this file's symmetric eps-normalization (both `g_evidence` and `g_prior` divided by the same `eps`) has an analogous bug to Task 5's real asymmetric-eps bug (`estimate_prior_reliance_map`, logged above) — confirmed it does not; the `eps` division is algebraically inert to the ratio here, since both terms scale by the same factor. Two MEDIUM findings addressed: (1) documented in the module docstring that a `forward_fn` insensitive to both `lr` and `z` produces a misleading `0` ("fully evidence-driven") rather than the more accurate "indeterminate" — the `1e-8` guard only prevents NaN/Inf, it doesn't distinguish the cases — and pinned that documented behavior with `test_fully_insensitive_forward_fn_returns_documented_zero_not_nan`; (2) added `test_result_is_invariant_to_eps_choice`, a regression guard specifically against reintroducing a Task-5-style asymmetric-eps bug in this file (the intended "known-correct" reference implementation), plus `test_equal_sensitivity_gives_mid_range_reliance` strengthening the existing valid-range test to also check calibration at the midpoint.

Tasks 8-10 (`KernelEstimator`, S3, S4) were implemented and reviewed together (3 parallel reviews). Real bugs found and fixed:
- `KernelEstimatorDataset` mutated a single shared RNG instance — silently duplicated across DataLoader workers and replayed identically every epoch. Fixed with a per-item `(seed, idx)`-derived RNG (same pattern now used everywhere else in this repo that needs per-item determinism).
- S3's `_MAX_EXPECTED_DISTANCE` normalizer was miscalibrated (hardcoded `4.0`) against the actual worst-case raw distance (~5.64 given the mismatch pool's real ranges), causing premature 1.0 saturation over ~45% of the mismatch-pool sigma range. Recalibrated from the pool's own range constants instead of a magic number.

- Two checkpoint-path bugs (`train_kernel_estimator.py`, `build_feature_bank.py`) hardcoding `"checkpoints"` regardless of `--out`'s actual directory.
- Documented-not-fixed limitations: kernel estimator's `theta` wraparound (pi-periodic kernel regressed via plain MSE) and target-scale imbalance (noise_sigma ~100x smaller than sigma/theta, gets negligible gradient); S4's curse-of-dimensionality separation loss at `k=5` on a sparse (~800-image) reference bank — confirmed via a production-scale synthetic proxy (N=800, D=384) that a near-duplicate query's `k=5` distance is barely distinguishable from a generic in-range point.

Tasks 11-14 were implemented together and reviewed in parallel (4 agents). This batch had the most consequential findings of the whole plan — several would have corrupted training supervision or produced meaningless reported numbers if shipped as originally written:
- **Task 11 (xSR-CausalBench), HIGH:** `build_prior_reliance_sample`'s label region was floor-aligned to the `scale=16` grid while the actual evidence-suppressed HR region wasn't — for small patches at unlucky offsets this could floor-align to an **empty** label region despite evidence being genuinely destroyed there (verified: `ph=10, y0=3` → label region `[0:0]`). Fixed to label the exact modified rectangle, matching how `build_distribution_shift_sample` already did it correctly. Added `test_prior_reliance_label_region_nonempty_even_for_small_unaligned_patch` as a regression guard.
- **Task 11, HIGH:** `CausalBenchDataset`'s `idx % len(ood_patches)` (idx is always `4*image_idx+3` for the distribution-shift procedure) collapses to 1-2 reachable patches for any power-of-two `ood_patches` pool size (e.g. `len==4` always selected `ood_patches[3]`, never 0-2) — silently destroying the intended OOD-texture diversity. Fixed to index by `image_idx` instead. Added `test_dataset_distribution_shift_uses_more_than_one_ood_patch` using visually-distinct patches to make the bug directly observable.
- **Task 11, MEDIUM:** `download_datasets.py` used plaintext `http://` and unvalidated `zipfile.extractall()` (Zip Slip risk). Verified the DIV2K host supports HTTPS and switched; added a safe-extraction check that rejects any archive member resolving outside the target directory.
- **Task 12 (fusion head), HIGH:** `reliability_head` had its own branch off the shared trunk but `train()`'s loss was `cross_entropy(cause_logits, ...)` only — no gradient ever reached `reliability_head`, so the "calibrated reliability score" the spec and this file's own docstring describe was actually random init, forever, regardless of training. Fixed by adding a `binary_cross_entropy` term against `label_map == RELIABLE`. Added `test_train_updates_reliability_head_parameters`, a regression test that would have caught this directly (asserts the head's weights actually change after `train()`).
- **Task 12, HIGH:** S1 (`compute_null_space_variance`) was the one fusion-head input channel left raw/unbounded while S2/S3/S4/luminance are all `[0,1]`-ish — reproducing the exact scale-mismatch problem the S4 `normalized_distance` fix (Task 10) was meant to solve, but for S1. Added `normalized_null_space_variance` (`src/signals/null_space.py`) using a domain-derived scale (theoretical max unbiased 2-sample variance for `[0,1]`-bounded pixel values = 0.5), and switched `build_signal_stack`/`run_chasr` to use it.
- **Task 12, MEDIUM:** the on-disk signal-stack cache (`precompute_signal_stacks`) had no fingerprint of the (dataset, k) configuration it was built from — a stale cache at the same path would be silently reused after e.g. changing the dataset seed or k, training on data that no longer matches the current run with no visible symptom. Fixed with a fingerprint check that raises on mismatch.
- **Task 12/14, HIGH (cross-task):** `run_chasr`'s default `k=4` didn't match `train_fusion_head.py`'s `TRAIN_K=2` — the fusion head was trained on S1 computed from `k=2` samples but evaluation (`run_evaluation.py`, "what produces every reported paper number") silently used `k=4` by default, a train/inference distribution mismatch on exactly the channel just normalized. Fixed by introducing `SIGNAL_STACK_K` (`src/fusion/train.py`) as the single source of truth, imported by `run_chasr`'s default, `train_fusion_head.py`'s `TRAIN_K`, and an explicit `k=SIGNAL_STACK_K` in `run_evaluation.py`'s call.
- **Task 13, MEDIUM:** `signal_correlation_matrix` had no `N<2` guard (silently returned all-NaN, unlike this repo's established fail-loudly pattern in `null_space.py`) — added the guard. `compute_lpips` had zero test coverage despite the codebase's established inject-for-testability pattern — added a stub-based test. `compute_psnr`'s divide-by-zero-then-clip approach for identical images produced a `RuntimeWarning` on every call — added an explicit `np.array_equal` short-circuit.
- **Task 13, follow-up flagged for Task 14:** per-image macro-averaged mIoU (what the plan's `run_evaluation.py` does) is not the standard dataset-level (accumulated-confusion-matrix) mIoU reported in most literature. Not fixed (would require a second aggregation path), but documented explicitly in `run_evaluation.py`'s docstring as a considered-but-not-yet-resolved methodology choice rather than something to assume was already settled.
- **Task 14, MEDIUM:** `test_infer.py` only checked `signal_stack`'s shape, not that the `[:4]` slice actually contains S1-S4 in order (vs. e.g. an off-by-one silently including luminance) — added a content-identity assertion using the stub's distinguishable constant-valued S3/S4 channels.

All of the above HIGH findings are now covered by regression tests, not just fixed in place — see the individual test files for the specific "this exact bug" tests.

## First real experiment run (2026-08-27)

Ran the full real-data pipeline end to end for the first time: `download_datasets.py` (DIV2K train_HR 800 images + valid_HR 100 images, ~4GB, via `curl` — the plan's `requests`-based downloader was untested and DIV2K's URL was `http://`, switched to `https://` per Task 11's review), `train_kernel_estimator.py`, `build_feature_bank.py`, `train_fusion_head.py`, `run_evaluation.py`. This is the first time any of Tasks 5, 8, 9, 12, 13, 14 ran against real data/real GPU rather than CPU stubs, and it surfaced several real bugs no unit test could have caught (stub-based tests, by construction, can't exercise real-device or real-multiprocessing behavior):

- **Windows `DataLoader(num_workers=2)` near-deadlock** (`scripts/train_kernel_estimator.py`): Windows' spawn-based multiprocessing has to pickle and IPC-transfer the entire `Dataset` object — including its ~400MB `hr_images` list — to every worker process before the first batch, observed taking many minutes (and leaving an orphaned process burning real CPU for hours after the parent task was killed) for a dataset this size. Fixed to `num_workers=0`; single-process loading is actually faster here.
- **Device-mismatch bugs in `compute_degradation_mismatch`, `run_evaluation.py`'s metric calls, and its `.numpy()` conversions** — real `nn.Module`/CUDA tensors mixed with CPU tensors straight from a `Dataset`, none of which the CPU-only stub tests in `tests/fusion/test_infer.py` could exercise. Fixed at the appropriate layer (inside the signal function for the reusable case, at the call site for the script-specific cases) — see the `fafecb0` commit for the full list.
- **`huggingface_hub`'s downloader stalling** on `train_fusion_head.py`/`run_evaluation.py`'s default hub repo id (the same issue logged for Task 5) — both scripts now accept the same `CHASR_MODEL_ID` local-snapshot override.
- **Repeated stale/orphaned GPU-holding processes**: multiple times during this session, a background task that had already reported completion (or been killed) left behind a Windows process still holding several GB of GPU memory and, in one case, actively burning CPU for hours. Not yet root-caused (plausibly `conda run`'s process-tree handling on Windows not cascading termination cleanly) — worked around each time via `Get-Process | Sort StartTime` + `Stop-Process`, not yet fixed in the codebase itself. Worth a real fix (e.g. a wrapper that tracks and cleans up its own child PIDs) if this pipeline is run unattended again.

**Real numbers obtained** (kernel estimator: 500 DIV2K train images [`train_kernel_estimator.py`'s hardcoded `max_images=500`, no CLI override — a subset of the same sorted file list], 20 epochs; feature bank: 800 DIV2K train images → `(800, 384)` DINOv2 embeddings; fusion head: 40 DIV2K valid images × 4 xSR-CausalBench procedures = 160 training items, `k=2`, 30 epochs; evaluation: 20 held-out DIV2K valid images, disjoint from training):

- Kernel estimator training loss: 1.63 → plateaus ~0.87-0.93 after epoch 1 (matches the already-documented target-scale-imbalance limitation — noise_sigma gets negligible gradient relative to sigma/theta).
- Fusion head training loss (cross-entropy + reliability BCE, combined): 1.98 → plateaus ~1.75-1.76 after epoch ~8. Modest but real learning: random-guess baseline for this combined loss is ≈ ln(5) + ln(2) ≈ 2.30.
- **PSNR: 19.16 dB, SSIM: 0.4194** — modest, as expected: PSNR/SSIM are context metrics per spec Section 5 item 1 (not the headline result), and low pixel-fidelity at 16x with a diffusion prior hallucinating null-space detail is the expected, motivating phenomenon this whole paper is about, not a defect.
- **Attribution pixel accuracy: 48.47%, mIoU: 29.85%** — the headline result (spec Section 5 item 3), on a 5-way classification task with a 20% random baseline: meaningfully above chance (~2.4x), but a modest first-pass result given only 40 training images and unweighted cross-entropy over the class-imbalanced benchmark (both already-documented limitations, not new findings).
- **S1-S4 disentanglement correlation matrix** (spec Section 5 item 5, spec Section 3's "Known risk — factor entanglement," required to be reported honestly rather than hidden):
  ```
          S1      S2      S3      S4
  S1   1.0000  0.2750 -0.0602 -0.0466
  S2   0.2750  1.0000 -0.0970 -0.1490
  S3  -0.0602 -0.0970  1.0000  0.1518
  S4  -0.0466 -0.1490  0.1518  1.0000
  ```
  Real, honest, and scientifically interpretable: S1 (null-space variance) and S2 (prior-reliance) show the strongest off-diagonal correlation (0.275) — consistent with the design spec's own prediction that "large ill-posedness naturally increases prior reliance." S3/S4 are close to uncorrelated with everything else. This is exactly the kind of entanglement evidence spec Section 3 asks the manuscript to report honestly.

**Scale caveat, to be stated explicitly in the manuscript, not glossed over:** this run used 40 training images / 20 held-out images — a small pilot-scale validation of the pipeline architecture and methodology, not the spec Section 3-recommended benchmark scale (~500-1000 images across DIV2K + Urban100 + Manga109). `TRAIN_MAX_IMAGES`/`EVAL_MAX_IMAGES` in the two orchestration scripts can be raised for a larger run; doing so was out of scope for this first end-to-end validation pass given the ~1-hour-plus wall-clock cost already observed at this small scale.

## Acting on the two deferred review items: bootstrap CI and capacity-matched control (2026-09-03)
